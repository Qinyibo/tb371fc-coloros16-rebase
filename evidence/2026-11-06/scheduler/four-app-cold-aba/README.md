真机记录确认 24 次冷启动。停用前台调度没有重复出现的收益，服务已恢复，参数保持原样。未刷机，未改变持久配置。硬件及长期稳定性尚未验收，`hardware_success_claimed=false`。

同一次启动，每段先丢弃一轮四应用冷启动，再采两轮。仅强停下一目标，系统确认目标主进程退出，再以 `am start -W` 启动并连续上滑两次。表格是每段两个 `TotalTime` 的范围。采样时活动显示模式为 120 Hz，GPU 下限 level 4，四扬服务运行，SELinux Enforcing。A1/B/A2 分组实读为 boost/prefer_idle 30/1、0/0、30/1，B 分组线程为空。第一次采集在 B 遇到锁屏，结果已剔除。

- 抖音采样时的焦点是 SplashActivity，QQ 是 LoginActivity。微信部分样本在上滑标记后没有帧。自动上滑只能定位采样窗口，无法给出手势到画面的端到端延迟或主观跟手。
- 两个开启段本身波动很大，温度也随轮次上升。例如 CPU0 传感器从 A1 的 67.7–77.5 °C 升至 A2 的 75.5–84.9 °C。这里没有温度导致卡顿或触发限频的因果结论。
- 事件日志记录到两次强停抖音时连带结束汽水音乐，理由是后者依赖抖音进程中的 SecShareDataProvider。测量窗口没有四个目标 App 的 `am_crash` 或 `am_anr` 事件。该结果不能判定已知的汽水私有堆扩展崩溃已修。
- 复测若关注独立冷启动，单独控制抖音与汽水的 provider 依赖。若关注内容页的跟手，使用能保持在固定重载内容页的第三方 App，并记录首屏及连续上滑是否实际响应。

[analysis.json](analysis.json) 包含逐次数据、FrameTimeline 每次访问的帧数和 P95、温度与采样状态。帧按 app、upid、surface frame token 去重，P95 是 FrameTimeline duration。[restoration.json](restoration.json) 记录调度回读与恢复到原息屏状态。

采集与查询脚本附在此目录。采集脚本以本地 D 盘工程根目录运行，依赖已有 ADB 服务、适配包的调试 root 和指定哈希的调度服务。执行前需替换设备序列号占位符。查询脚本依赖工程的 `tools/trace_processor_shell.exe`。原始 Perfetto、事件日志和设备标识保存在 D 盘，仓库保留筛选后的结果。

## 试验结束后的无法唤醒反馈

试验结束时，调度已恢复至亮屏 `30/1`，随后按测试前状态息屏。用户后来报告无法唤醒。再次只读连接时，启动 ID 已变化，系统启动原因只返回 `reboot`，pstore 为空。缺本次失效窗口的 main 与内核现场，无法判定是强制重启、系统重启还是其他触发。约 88 °C 是 A2 测量期间的 CPUSS0 峰值，故障当时的温度未知。黑屏／触控问题仍未根治。
